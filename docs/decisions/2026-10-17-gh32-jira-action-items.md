# Decision Record: 승인된 회의록의 액션 아이템을 Jira 이슈로 만듦

> Created at: `2026-10-17`
> GitHub Issue: `#32`
> Status: Accepted (1~3은 사용자 결정. 4~7은 작업 판단이며 PR 리뷰에서 확인받는다)

## Context

2026-10-17 스프린트 등 일정 관리가 ClickUp에서 Jira로 옮겨졌다. Jira에는 Qello 프로젝트(`SCRUM`, 팀 관리형)가 있다. 보드 1에서 스프린트는 파트별로 나뉜다
(`Backend·Sprint 3 (12/10–18/10)`, `Android·Sprint 3 (12/10–18/10)`). 같은 기간에 진행 중 스프린트가 여럿이다.
Confluence `스프린트 작업 연결 규칙`에 따르면 주간 계획에서 합의한 작업만 파트별 스프린트에 넣고, 주 1회 정기 회의에서 그 주 스프린트를 같이 정한다.
회의록 템플릿의 `## 액션 아이템` 표에는 담당 파트, 담당자, 할 일, 기한, 작업 링크 칸이 있다. Jira에 초대된 계정은 아직 한 명뿐이다.

## Decision

1. (사용자) 승인된 회의록의 액션 아이템마다 Jira 이슈를 하나 만든다. 승인 버튼이 이슈 만들기의 승인이다. 승인 메시지에 이 사실을 적는다.
2. (사용자) 스프린트는 담당 파트의 진행 중·예정 스프린트 중 기한이 기간 안에 드는 것에 넣는다. 기한이 없거나 맞는 스프린트가 없으면 백로그에 둔다.
3. (사용자) Confluence `회의록 템플릿`의 `ClickUp 작업` 열 이름을 `Jira 이슈`로 바꾼다(열 이름만). 에이전트가 배포 직전에 바꾼다.
4. (작업 판단) 이슈는 `작업`(`10003`) 유형으로 만든다. 요약은 할 일, 기한은 `YYYY-MM-DD`일 때만, 레이블은 `meeting-minutes`와 `meeting-<회의 ID>`,
   설명(ADF)은 회의록 이름, 담당 파트, 담당자 이름이다. 담당자 칸은 비운다. 표시 이름으로 Jira 계정을 찾으면 틀린 사람에게 배정될 수 있고,
   지금은 팀원 계정이 없다.
5. (작업 판단) 스프린트는 이름이 담당 파트로 시작하고 `sprint`를 포함하며 시작·끝 날짜가 있는 진행 중·예정 스프린트 중, 한국 날짜로
   시작 ≤ 기한 ≤ 끝인 것이 정확히 하나일 때만 넣는다(스프린트 필드 `customfield_10020`). 둘 이상이면 고르지 않고 백로그에 둔다.
6. (작업 판단) 같은 제목의 회의록이 있어 쓰지 않을 때는 이슈도 만들지 않는다. 이슈 만들기는 재시도하지 않는다. 대신 만들기 전에
   `meeting-<회의 ID>` 레이블 이슈를 검색해 요약이 같은 것은 다시 만들지 않는다. 표의 이슈 칸에 이미 키가 있는 행도 새로 만들지 않는다.
7. (작업 판단) 이슈를 먼저 만들고 키를 회의록 표에 링크로 채운 뒤 Confluence에 쓴다. 페이지를 한 번만 쓰고(고쳐 쓰지 않음), 다시 읽은 대조가
   채운 본문 그대로를 기준으로 한다. 자격 증명은 #31의 Atlassian Basic Auth(클래식 토큰)를 같이 쓴다.

## Rationale

- 행을 고르는 일, 스프린트를 고르는 일은 정해진 규칙이라 코드가 한다(AGENTS.md 3.2). LLM이 이슈를 만들지 정하지 않는다.
- 회의 날 스프린트가 바뀌는 중이어도 기한으로 고르면 끝나 가는 스프린트에 잘못 들어가지 않는다.
- 레이블과 요약으로 이미 만든 이슈를 찾으면, 실패 뒤 다시 처리해도 이슈가 두 번 생기지 않는다. 이슈 만들기를 재시도하지 않는 원칙과 함께 쓴다.
- 이슈를 먼저 만들면 회의록에 링크가 들어간 채로 한 번만 쓴다. 페이지를 먼저 쓰고 고치면 Confluence 쓰기가 두 번이 되고 버전 충돌을 다뤄야 한다.

## Alternatives considered

| Alternative | Advantages | Disadvantages | Reason not selected |
| --- | --- | --- | --- |
| 파트의 진행 중 스프린트에 넣기 | 기한이 없어도 스프린트에 들어간다 | 회의 날 스프린트가 바뀌는 중이면 끝나 가는 스프린트에 들어간다 | 사용자가 기한 기준을 골랐다 |
| 백로그에만 두기 | 단순하다 | 사람이 다시 옮겨야 한다 | 사용자가 기한 기준을 골랐다 |
| Confluence에 먼저 쓰고 이슈를 만든 뒤 페이지 고치기 | 이슈 설명에 페이지 링크를 넣을 수 있다 | Confluence 쓰기가 두 번이고 버전 충돌을 다뤄야 한다 | 쓰기를 한 번으로 둔다 |
| 담당자 이름으로 Jira 계정 찾기 | 담당자가 채워진다 | 표시 이름이 같거나 비슷하면 틀린 사람에게 배정된다. 지금 계정이 없다 | 계정이 생기면 별도 Issue로 연결 표를 둔다 |
| 이슈 만들기 재시도 | 일시 오류에 강하다 | 응답을 못 받고 다시 보내면 두 개가 생긴다 | 레이블 검색으로 다시 처리를 안전하게 했다 |

## Evidence

- Atlassian 연결로 읽은 실제 Jira(2026-10-17): 프로젝트 `SCRUM`(id `10000`, 팀 관리형), `작업` 유형 `10003`의 만들기 화면 필드(필수: 프로젝트, 요약,
  보고자 기본값. 선택: 담당자, 기한, 레이블, 스프린트 `customfield_10020`, 설명), 보드 1의 파트별 스프린트 이름과 기간.
- [Jira REST v3 이슈 만들기](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/): 설명은 ADF다.
- [Jira Software 스프린트 API](https://developer.atlassian.com/cloud/jira/software/rest/api-group-board/): 보드의 스프린트를 `state`로 거른다.
- [스프린트 필드로 이슈 만들기](https://support.atlassian.com/jira/kb/creating-an-issue-in-a-sprint-using-the-jira-rest-api/): 스프린트 필드에 스프린트 숫자 ID를 넣는다.
- 오프라인 테스트와 E2E(실제 n8n 2.42.6, 가짜 Jira)에서 행 고르기, 스프린트 고르기, 다시 처리할 때 이슈 재사용, 링크 채우기, 실패 알림을 확인했다.
- 확인할 것: 실제 Jira에서 스프린트 필드를 만들기 때 넣을 수 있는지, 새 검색 API(`/rest/api/3/search/jql`)가 방금 만든 이슈를 바로 찾는지.

## Data and cost

- 외부로 전송되는 데이터: 승인된 회의록의 액션 아이템(할 일, 담당 파트, 담당자 표시 이름, 기한)과 회의 ID가 Jira에 간다. 팀 일정이 이미 Jira에 있다.
- 예상 호출량: 회의당 Jira 호출 2회 + 액션 아이템 수(검색, 스프린트 목록, 이슈 만들기 N회). 요금은 지금 Jira 요금제 그대로다.
- 교체 시 영향: 템플릿 열 이름을 바꾸기 전에 배포하면 이슈는 만들되 회의록 표에는 링크를 채우지 못하고 메시지에 그렇게 적는다.

## Consequences

### Positive

- 회의에서 정한 할 일이 사람 손을 거치지 않고 파트 스프린트에 들어간다. 회의록과 이슈가 서로 링크된다(Confluence의 이슈 링크는 Jira에도 보인다).

### Negative / risks

- 승인된 회의록의 할 일 문장이 그대로 이슈 요약이 된다. 문장이 길거나 모호하면 이슈도 그렇다. 승인 전에 `수정`으로 고친다.
- 스프린트 이름 규칙(`<파트>·Sprint N`)이 바뀌면 모두 백로그에 들어간다.
- 담당자는 비어 있어 스프린트 계획 때 사람이 채운다.

## Revisit conditions

- 팀원 Jira 계정이 생겨 담당자를 자동으로 채우고 싶을 때
- 스프린트 이름 규칙이나 보드가 바뀔 때
- 액션 아이템이 한 회의에 50개를 넘을 때(검색 한도 100개)
