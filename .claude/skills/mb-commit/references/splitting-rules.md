# 커밋 분할 기준

`AGENTS.md` 5절 "하나의 커밋에는 하나의 검토 목적만 담는다"의 실행 규칙이다.

## 하나의 검토 목적이란

리뷰어가 **한 번에 한 가지 질문만** 던지게 되는 단위다.

- "녹음이 시작과 종료 사이에만 일어나나?" — recorder 커밋
- "근거 없는 결정 항목이 Confluence에 가지 않나?" — 워크플로 커밋
- "n8n이 밖에서 열리지 않나?" — 배포 커밋

한 커밋을 보며 두 가지 이상을 판단해야 하면 나눈다.

## 분할 축

우선순위 순으로 적용한다.

1. **처리 단계** — 녹음 / 마무리·변환 / n8n 전달 / 음성 인식 / 회의록 생성 / 근거 검증 / 승인 / Confluence 쓰기·Discord 알림
2. **타입** — 기능 추가와 리팩터링을 섞지 않는다. 포맷팅이나 이름 변경만 있는 파일은 별도 커밋으로 뺀다.
3. **실행 위치** — 봇 코드, n8n 워크플로 JSON, Docker·서버 설정은 나눈다.
4. **부수 작업** — 의존성 추가, 설정 변경, 문서와 결정 기록은 구현과 분리한다.

## 순서

앞 커밋만으로 실행과 테스트가 깨지지 않도록 의존성의 아래에서 위로 쌓는다.

```text
결정 기록 → 의존성·설정 → 봇 코드 → n8n 워크플로 → Docker·배포 설정 → 테스트 → 문서
```

작은 버그 수정과 회귀 테스트처럼 같은 커밋이어야 검토가 쉬운 경우는 합쳐도 된다.
그때는 초안에 이유를 적는다.

## scope 선정

소문자, 숫자, 하이픈만 쓴다. 다음은 시작용 목록이며 실제로 쓰인 scope가 생기면 이 표를 갱신한다.

| scope | 대상 |
| --- | --- |
| `recorder` | Discord 녹음 봇, 슬래시 명령, 마무리·변환 |
| `workflow` | n8n 워크플로 JSON, 프롬프트, 근거 검증 Code 노드 |
| `deploy` | Dockerfile, docker-compose, 서버 설정 |
| `harness` | `AGENTS.md`, `CLAUDE.md`, Skill, 검사 스크립트 |
| `github` | Issue·PR 템플릿, GitHub Actions |
| `docs` | README, 다이어그램, 결정 기록 |

적당한 scope가 없으면 생략한다.

## 타입 선택

| type | 사용 |
| --- | --- |
| `feat` | 새 동작·기능 |
| `fix` | 결함 수정 |
| `refactor` | 외부 동작을 유지하는 구조 변경 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서·설계 산출물 |
| `chore` | 도구, 자동화, 의존성 |
| `ci` | GitHub Actions 워크플로 |
| `build` | Dockerfile, 패키징 |
| `perf` | 성능·비용 개선 |

브랜치 prefix가 있으면 커밋 type을 맞춘다. 브랜치 타입을 벗어나는 변경이 크면 다른 작업으로 분리할지 묻는다.

## 커밋하면 안 되는 것

- `.env`, 로컬 설정, 자격 증명, 토큰
- 녹음 파일, `recordings/`, 녹취 원문, 참석자 ID가 든 manifest
- `node_modules/`, `__pycache__/`, IDE 파일, 로그
- 자격 증명 값이나 서버 주소가 남은 n8n 워크플로 JSON
- 스크래치 파일, 실험 코드, 주석 처리된 디버그 코드
- 다른 사람이 작업 중인 파일의 무관한 변경

발견하면 커밋에서 빼고 사용자에게 보고한다.

## 나누지 못하는 경우

한 파일 안에 여러 목적이 섞여 있으면 hunk를 자동으로 쪼개지 않는다. `git add -p`는 대화형이라
에이전트가 실행할 수 없다. 두 가지를 제안한다.

1. 한 커밋으로 합치고 커밋 본문에 두 목적을 나눠 적는다.
2. 사용자가 `! git add -p <파일>`로 직접 나눈 뒤 Skill을 다시 실행한다.
