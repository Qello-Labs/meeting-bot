# PR 작성 규칙

PR 제목과 본문을 쓰거나 고칠 때 적용한다. 처음 보는 리뷰어가 한 번 읽고 무엇을 왜 바꿨고 무엇을 확인했는지
알 수 있게 쓴다. 사실과 근거만 남기고 홍보 문구와 상투적 표현을 뺀다.

## 1. 제목

- `<type>: <한국어 요약>`이다. `type`은 브랜치 접두사와 같게 쓰고 scope는 쓰지 않는다.
- 요약은 명사형으로 끝내고 브랜치 전체 작업을 한 줄로 담는다.
- GitHub Issue가 있으면 본문에 `Closes #<번호>`를 넣는다.

## 2. 본문 구성

- 미리 써 둔 초안이나 템플릿에 값만 채우지 않는다. 이 문서를 읽은 뒤 처음부터 쓴다.
  `.github/PULL_REQUEST_TEMPLATE.md`는 담을 내용의 목록이다. 칸 이름과 안내 주석은 남기지 않고 문장으로 바꾼다.
- 3,000자 이하로 쓴다. 본문 파일의 글자 수(링크 주소 포함)로 잰다.
- 결정 근거, 대안 비교, 커밋별 설명은 `TASK.md`, 결정 기록, 보고서에 두고 본문에는 결론과 링크만 둔다.
- 같은 내용이나 수치를 두 번 쓰지 않는다.
- 완료 조건 표는 `확인한 것 | 결과` 두 칸으로 쓴다. 증빙은 결과 칸에 링크로 붙인다.
- 저장소 파일 링크는 지금 커밋에 고정한 주소(`https://github.com/<저장소>/blob/<커밋>/<경로>`)로 걸고
  링크 글자는 한국어로 쓴다. 주소 안의 커밋은 보이지 않으므로 아래 4절 금지에 해당하지 않는다.

담는 순서는 다음을 기본으로 한다. 해당 없는 항목은 사유를 한 문장으로 쓴다.

1. `Closes #<번호>`
2. 무엇을 왜 바꿨는지. 해당할 때만 녹음·녹취 데이터 처리, 외부 API 전송, Confluence·Jira·Discord 쓰기, 서버·n8n 설정, 비용 영향
3. 완료 조건 표
4. 실행하지 못한 검증과 이유·후속 방법
5. 남은 위험과 되돌리는 방법
6. 템플릿의 리뷰 확인 체크박스

## 3. 종결 어미는 합쇼체

본문의 모든 서술은 `~합니다`, `~했습니다`, `~입니다`로 끝낸다.

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| 전송 단계를 추가한다. | 전송 단계를 추가했습니다. |
| 검증은 통과했다. | 검증은 통과했습니다. |
| 영향은 없다. | 영향은 없습니다. |

예외:

- **PR 제목** — summary는 명사형으로 끝낸다.
- **인용** — Issue 본문, 로그, 문서를 그대로 인용할 때는 원문 말투를 유지한다.
- **저장소 규범 문서** — `AGENTS.md`, `docs/`, Skill 문서는 평서체(`~한다`)가 기준이다. PR 본문과 혼동하지 않는다.

## 4. 쓰지 않는 것

| 금지 | 이유 | 대신 |
| --- | --- | --- |
| 커밋 해시, 브랜치 이름, CI 실행 ID, 작업 폴더 경로 | 리뷰어에게 뜻이 없고 rebase나 병합 뒤에는 틀린 값이 된다 | 쓰지 않는다. CI 실행은 `[실행 기록](URL)`처럼 한국어 글자에 링크를 건다 |
| 풀어 쓰지 않은 영어 용어 — artifact, worktree, concurrency | 처음 보는 리뷰어가 뜻을 찾아야 한다 | 결과 파일, 별도 작업 폴더, 앞 실행 취소처럼 한국어로 쓴다. GitHub 화면에 보이는 이름이나 검색할 원어가 필요하면 처음 한 번만 괄호로 함께 쓴다 |
| 코드 서식, 굵은 글씨, 불릿 남발 | 전부 강조하면 아무것도 강조되지 않는다 | 문단으로 쓴다. 코드 서식은 그대로 입력할 명령과 파일 이름에만, 목록은 실제 열거에만 쓴다 |
| 이모지 | 리뷰 노이즈이고 검색·diff를 방해한다 | 텍스트로 쓴다 |
| 과장 형용사 — 완벽한, 강력한, 혁신적인, 매끄러운, 손쉽게, 깔끔하게 | 검증할 수 없는 주장이다 | 무엇이 어떻게 달라졌는지 사실로 쓴다 |
| 근거 없는 정도 부사·자기 평가 — 대폭, 크게, 매우, 상당히, 크게 개선했습니다, 최적화했습니다 | 측정값이 없으면 뜻이 없고 판단은 리뷰어 몫이다 | 변경 내용과 측정값만 쓴다 |
| 인사말·맺음말 — 안녕하세요, 리뷰 부탁드립니다, 감사합니다 | PR 본문은 편지가 아니다 | 넣지 않는다 |
| 상투적 도입·마무리 — 이번 PR에서는, 요약하자면, 결론적으로, 앞으로 ~할 것으로 기대됩니다 | 내용 없는 연결어다 | 바로 본론을 쓴다 |
| 번역투 — ~을 통해, ~에 대해서, ~에 있어서, ~하는 것이 가능합니다, ~을 진행하였습니다 | 영어 구문을 직역한 어색한 한국어다 | ~로, ~는, ~할 수 있습니다, ~했습니다 |
| 피동 남용 — 되어집니다, 보여집니다 | 이중 피동이고 주체가 흐려진다 | 능동으로 쓴다 |
| 1인칭·감정 — 제가, 저는, 아쉽게도, 다행히 | PR은 변경 사실을 적는 문서다 | 주어 없이 사실만 쓴다 |
| 기계적 3항 나열 | 항목 수를 맞추려고 없는 내용을 만든다 | 있는 만큼만 쓴다 |
| 작성 도구 이름과 서명 줄 — Generated with ... | 리뷰에 필요 없는 정보다 | 넣지 않는다 |

## 5. 사실과 검증

- 실행한 검증은 명령과 결과를 그대로 쓴다.
- 실행하지 않은 검증은 하지 않았다고 쓰고 이유와 후속 방법을 적는다. "문제없을 것입니다"로 대신하지 않는다.
- 추측은 추측이라고 밝힌다. "영향이 없습니다"와 "검색 코드 변경이 없어 영향이 없다고 판단했습니다"는 다른 문장이다.
- 시간·비용·품질 수치는 측정 기간, 회의 수, 모델과 함께 쓴다. 오프라인 테스트, 계산·추정, 실제 운영 결과를 구분한다.
- 로컬 검증이나 push 전 자동 검사를 건너뛰었으면 그 사실, 대신 돌린 검증과 결과, 남은 위험을 적는다.
- 위험과 되돌리는 방법을 빼지 않는다.

## 6. 제출 전 점검

- [ ] 커밋 해시, 브랜치 이름, CI 실행 ID, 작업 폴더 경로가 없는가
- [ ] 영어 용어를 풀어 썼는가
- [ ] 3,000자 이하인가
- [ ] 템플릿 칸 이름과 안내 주석이 남지 않았는가
- [ ] 같은 내용이나 수치가 두 번 나오지 않는가
- [ ] 실행하지 않은 검증을 통과로 쓰지 않았는가
- [ ] 모든 서술이 합쇼체이고 4절의 금지 표현이 없는가
- [ ] 처음 보는 사람이 한 번에 읽을 수 있는가

하나라도 걸리면 고친 뒤에 사용자에게 초안을 보여준다.
